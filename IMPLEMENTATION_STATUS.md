- **Run 12 — calibrate the verdict by confidence (the instrument stops lying about itself)**: Run 11 still let the deep case cry `a hologram, not a diamond` — but in this system a *solid* Verified/Live stratum is **execution-earned** (the test genuinely passed, the binary genuinely ran), so sparse topology cannot *prove* a deep claim fake; it is at most a weak proxy for a **stub** probe. A definitive fakeness verdict there is a lie the instrument can't honestly make — and the capstone pins "the system does not lie." So the deep case is now a *calibrated suspicion* that names the real residual risk rather than a verdict: `⚠ over-fit suspect — a {live} claim stands over a sparse topology (d); confirm the probe is substantive, not a stub (a hologram passes too)`. Definitive structural holograms (a stratum floating above a hollow base) keep their own line and prevent full solidity anyway, so they never reach this verdict. The three outcomes (genuine / suspect / thin-but-shallow) live in one testable `honesty_verdict(cube, d, color) -> Option<String>`; the render just calls it. Still advisory, still render-only; the epistemic gain is that the instrument now distinguishes what it *knows* (structural) from what it *suspects* (topological), and never accuses earned work of being fake.
- **Run 13 — the delta (`--since`): the instrument gains time**: until now every reading was a single snapshot of the present. Run 13 adds the temporal dimension — the question the AI age actually asks: *"a change touched my workspace; what did it realize, what did it break?"* `--since <baseline>` measures the wish against a prior `--wish-session` snapshot (same wish required, matched by id) and renders what moved: `+ gained` (facets newly met), `✗ regressed — the change broke a met facet` (the alarm), and the held / still-missing counts. Deterministic (facets ordered by rendered label, no wall clock), read-only (nothing written), advisory. One pure `delta_report(wish, baseline, current, color)`, wired into the read-only human path; `--since` joins the parser, the `--help`, and the pinned doors catalog. Tests: a unit test (gain, regression, unchanged) and an end-to-end round trip (`tests/delta.rs`: snapshot → edit → `--since` names the newly-realized facet; a missing baseline says so). Live smoke caught a simultaneous `+ Module beta` and `✗ Symbol f` in one reading. The snapshot file *is* the baseline — re-measuring against it is the regression test for a wish.
- **Run 14 — the delta becomes machine-actionable (from observer to guardian)**: Run 13's delta was visible; Run 14 makes it *act*. The diff is now one pure, serializable `WishDelta { wish_id, gained, regressed, held, still_missing }` computed once and shared by three consumers — the human render, `--since --json` (a self-describing machine delta carrying the content-addressed `wish_id`), and a **regression exit code**: when a change broke a previously-met facet, the run exits **2** — distinct from `1` ("still incomplete") and `0` ("realized") — so CI can gate specifically on *"you broke something that worked"* (`… --since base.json . || [ $? -eq 2 ] && fail`). This stays inside CROSS-010: only the realization status gates (it always did); `--since` merely gives the *unrealized* code more resolution, while the advisory signals (honesty, density) still never gate. Tests grew to four end-to-end cases (gain→exit 0, regression→exit 2, `--json` shape, missing baseline) plus the unit diff; live smoke: baseline realized→0, break beta→2, JSON `regressed: ["Module beta"]`. The instrument can now stop a bad change, not just describe it.
- **Run 15 — the wishlist: from a wish to a project**: every run so far measured *one* wish. Run 15 scales the instrument up a level — `--wishlist <file>` reads many prose wishes (one per non-`#` line) and measures them all against the workspace as a project's *definition-of-done*, into an aggregate `realized N/M` gauge with a marked line per wish (`✓ a module alpha (1/1)` … `✗ a module beta (0/1)`). Its own read-only, deterministic mode (a sibling of `--pruefstand`, exclusive with `--wish`): the workspace is observed *once*, at the deepest level any wish in the list needs (a deeper observation still answers shallower facets), then every wish is assessed against that single observation. Exit 0 only when *every* wish is realized — the project gate (CROSS-010: realization status gates, nothing else). `--wishlist --json` emits a machine project gauge (`{realized, total, wishes:[{wish, realized, met, total}]}`). `--wishlist` joins the parser, `--help`, and the pinned doors catalog as a first-class door. Tests: a unit aggregate render + four end-to-end cases (aggregate `realized 2/3` → exit 1, all-realized → exit 0, JSON gauge, exclusive-with-`--wish`). Live smoke: a four-line `.wishes` file read `realized 3/4`, exit 1.
- **Run 16 — the project delta (time × project)**: Run 13's time-axis met Run 15's project-axis. A wishlist `--json` reading is now self-describing (each row carries its content-addressed `wish_id`) and re-readable, so it *is* a baseline. `--wishlist <file> --since <reading>` diffs the whole project against a prior snapshot — matched per wish by `wish_id`, so a re-edited prose line still tracks — and renders which whole wishes *newly realized* and which *regressed* (`✗ regressed 1 — wishes that were realized are no longer: a module alpha`). The CI question of the PR age, answered by an exit code: a project regression exits **2** (distinct from `1` incomplete, `0` all-realized), so `--wishlist f --json . > base` then `--wishlist f --since base . || [ $? -eq 2 ] && fail` gates a PR on *"did this break any project wish?"*. `WishlistDelta::compute` matches by id via a `HashMap`, builds its lists in wishlist-file order (deterministic), and `--since --json` emits the machine delta. Tests: a unit (aa regressed + bb newly realized in one diff) and two end-to-end cases (regression→exit 2 naming the broken wish; progress→exit 0). Live smoke: break a module → `regressed 1`, exit 2. The instrument now guards a *project* across time, the same way it guards a single wish.

### kosmo-sandbox — the execution sandbox (Runtime floor, beam 2) (2026-06-04)
